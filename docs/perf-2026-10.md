# Where video export time goes (October 2026)

Measured on the three current video scenes in `monocurl-examples/videos`
(`barnette2`, `cdc2`, `knot`), medium resolution (1920x1080), 60 fps, on the
M-series dev machine (6 performance + 2 efficiency cores). Scenes were snapshotted
before measuring, since other agents regenerate them.

Production renders go through `pipeline/prender.py`, which runs about 8
`monocurl video --slides` processes at once. The machine is saturated, so what
matters is **CPU time per frame**, not wall-clock time of one process.

## Method

- Phase 1, startup: `/usr/bin/time -l monocurl video SCENE --list-slides` (parse,
  compile, then a seek to the end of the scene).
- Phase 2, per frame: `MONOCURL_EXPORT_TIMING=1 monocurl video SCENE --slides N
  --start-time A --end-time B` prints eval / render / encode ms per frame.
  `sample <pid> 6` on a running export splits each phase further.
- A/B: the old binary is copied aside before rebuilding; both run back to back,
  min of 2. Output MP4s are compared with `cmp`.

## Phase 1: startup

| scene | wall | CPU | peak RSS | video length |
|---|---|---|---|---|
| barnette2 | 1.3 s | 0.25 s | 106 MB | 1253 s, 75k frames |
| cdc2 | 0.19 s | 0.18 s | 47 MB | 1845 s, 111k frames |
| knot | 4.3 s | 8.2 s | 1.5 GB | 1420 s, 85k frames |

The timeline seek skips animation in-betweens, so startup is small next to
rendering, except for knot, whose 3.8 MB scene and data tables cost a few
seconds and 1.5 GB per process.

## Phase 2: per frame (before this round)

| scene, chunk | eval | render | encode | encoder thread split |
|---|---|---|---|---|
| barnette2, slide 3 | 0.2 ms | 2.4 ms | 21.2 ms | |
| cdc2, slide 2 | 0.1 ms | 1.5 ms | 19.8 ms | |
| knot, slide 5 | 79.5 ms | 4.8 ms | 21.5 ms | |

For the 2D scenes the **H.264 encoder is ~90% of the CPU**. A profile of the
encoder thread on barnette2:

- 45%: OpenH264's screen-content feature search preprocessing
  (`PerformFMEPreprocess`: `width_loop8x8_2`, `hash_width_loop`), enabled by
  `UsageType::ScreenContentRealTime`.
- 26%: RGB to YUV conversion (`YUVBuffer::from_rgb_source`), which walked the
  frame column by column with per-pixel float FMAs.
- 22%: actual slice coding.

For knot, eval dominates: the kernel tier's lane machine running dynamic list
arithmetic and `lerp` on `KVal` lists (malloc per op) for the tubes' shading
callbacks.

## Changes

| change | effect | output |
|---|---|---|
| integer, row-major YUV conversion (`exporter/src/yuv.rs`, #108) | encode 21.2 -> 17.1 ms (barnette2), 17.8 -> 13.7 ms (cdc2); ~20% less CPU per 2D frame | byte-identical MP4 |
| unboxed short numeric lists in typed kernels (#109) | knot CPU per 120 frames: slide 5 43.2 -> 28.9 s, slide 0 49.3 -> 36.8 s; default scenes unchanged | byte-identical MP4 and stills |
| native code for vector programs (#110; JIT: vector registers, captured tables, boxed vectors, `lerp` on numbers, `len`) | knot CPU per 120 frames vs #109: slide 5 27.4 -> 11.1 s, slide 0 34.2 -> 21.2 s, slide 6 30.6 -> 26.5 s (each includes ~8 s of startup) | byte-identical MP4 |
| `round`/`floor`/`ceil`/`trunc` and `min`/`max` of run-time-kind numbers inline in native code | knot slide 0 21.1 -> 18.9 s per 120 frames; slides 5 and 6 unchanged | byte-identical MP4 |
| OpenH264 camera usage type instead of screen content | encode 17.5 -> 6.6 ms (barnette2), 13.7 -> 3.7 ms (cdc2), 18.5 -> 6.8 ms (knot) a frame | bitstream changes; PSNR/SSIM vs lossless stills equal to four digits |

## Where knot frames stand after these changes

CPU per 120 medium frames, startup (~8 s) included, chaining the A/Bs above
(each pair was measured back to back, but the pairs ran at different machine
loads, so this is approximate): slide 5 about 43 -> 11 s, slide 0 about 49 ->
19 s, slide 6 about 31 -> 26 s. On slide 5 the encoder (~16 ms
a frame) is now the largest cost; slide 6 still runs most of its callbacks on
the typed machine.

## Open leads

- Encoder: OpenH264's screen-content usage type spends about half the encoder
  thread on a feature search. The camera usage type, measured on barnette2,
  cdc2 and knot chunks: encode 17.5 -> 6.6, 13.7 -> 3.7 and 18.5 -> 6.8 ms a
  frame, 57-67% less CPU on 2D frames, files 5-9% larger on 2D and 4% smaller
  on knot, PSNR and SSIM against lossless stills equal to four digits. It
  changes the bitstream, so it waits for a decision (local branch
  `perf/encoder-camera-usage`).
- 33-48% of 2D frames are static (ffmpeg mpdecimate on the drafts); skipping
  their encode would need variable frame durations, which prender.py's
  packet-count check and editors would have to accept.
- knot slide 6: vector programs decline on calls the specialiser does not
  inline (callees over 256 ops) and on indexing lists the body built; the
  latter is a read from the list site's area.
- Build iteration: release is fat LTO with one codegen unit, 8-18 minutes per
  rebuild here. A separate thin-LTO profile for local iteration would cut that
  without touching shipped binaries.
