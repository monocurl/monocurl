# Rust scene MVP design

The authoring representation is intentionally static. A live call is a normal
Rust struct with one field per label; it is not an argument map or dynamic
`Value` tree. The `live!` macro only saves typing when that call needs to be
retained, labeled, and edited later.

```rust
live! {
    fn ball(center: Vec2, radius: f64, color: Color) -> Result<MeshValue> {
        Ok(MeshValue::circle(center, radius, color))
    }
}
```

Conceptually expands to a concrete `Ball { center, radius, color }`, a plain
`ball(...) -> Ball` constructor, `Recipe for Ball`, and a `BallMeshExt` trait
giving `Mesh<Ball>` typed `center`, `radius`, and `color` attributes.

For static construction, users write ordinary Rust and implement `Recipe`
directly. `examples/overview.rs` shows this with `StaticCircle`; it needs no
macro because it has no labels to mutate.

## Operators

`live! { operator fn ... }` generates a generic wrapper such as
`Shift<Target>`. The wrapper preserves its target and labeled arguments in its
type. It implements `Recipe::interpolate_from` with the Monocurl operator rule:
interpolate the operand first, evaluate the operator identity/modified pair on
that operand, then interpolate between those endpoints.

Generated extension traits intentionally make nested access explicit:

```rust
scene.delta().set(UP);
scene.target().radius().set(0.7);
```

This avoids field-name ambiguity between an operator and its target while
remaining compile-time checked.

## Alternatives to evaluate

1. Keep `live!` as the only macro. This is the current MVP: use it only for
   named editable recipes and operators; everything else is a normal struct or
   function.
2. Add `#[derive(Recipe)]` for users who prefer writing their concrete struct
   first. The derive would generate `Recipe` plus typed attribute traits, while
   evaluation remains a normal manually written method.
3. Add a small `scene!` block only for slide/play sequencing. It should not be
   used for mesh construction or ordinary algorithmic Rust.

The recommended direction is (1), then optionally (2). It keeps the runtime
model explicit and makes generated code easy to inspect with macro expansion.

## Type-changing keyframes

This is the main constraint exposed by the static MVP. MCL permits a leader to
change from `Ball(...)` to `shift{...} Ball(...)`; their available attributes
are not identical. A literal `Mesh<R>` cannot accept both `Ball` and
`Shift<Ball>` as `set` values without erasing `R`.

Do not hide this with an all-purpose dynamic `Value`. The low-magic choices are:

1. Use a concrete scene-state enum when one leader intentionally has several
   shapes:

   ```rust
   enum DotState { Ball(Ball), Shifted(Shift<Ball>) }
   ```

   A derive can implement `Recipe` and expose only the common attributes.
2. Keep a stable outer recipe and mutate its typed fields. This covers most
   `Lerp` use: `dot.center().set(...)`, `dot.color().set(...)`, and similar
   updates do not change the recipe type.
3. At the runtime boundary only, allow `Mesh<Schema>` to store
   `Box<dyn Recipe<Schema>>`. `Schema` remains a compile-time type generated by
   the macro, so attribute access is still static; only the selected keyframe
   implementation is erased. This is likely necessary for full MCL parity, but
   should be introduced only after explicit enum state families prove too
   verbose.

The MVP currently illustrates (2) and uses a new typed leader for a later
different recipe in `overview.rs`. This is intentional: it makes the design
tradeoff visible instead of concealing it.
